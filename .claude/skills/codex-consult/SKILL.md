# Codex 合議

Codex を read-only の相談役として呼び、独立した意見を得る。主導権は Claude Code が持つ。意見が割れたら事実確認をしながら議論し、合意できなければユーザーに判断を仰ぐ。議論の内容は必ずユーザーに伝える。

## 呼び出し方

Codex は必ずこの skill のディレクトリにある `run.py` 経由で呼ぶ。`codex exec` を直接実行しない。`run.py` は次を強制する。

- 安全: `-s read-only`、`--ignore-rules`（同期された allow ルールは sandbox の外でコマンドを実行してしまう）、`approval_policy="never"`、`--skip-git-repo-check`。さらに hooks（genshijin などが回答方針を変えてしまう）と、apps・plugins・computer_use・browser_use などコマンドの sandbox の外に届く機能を無効にする
- モデルと effort の許可リスト
- 相談ごとのディレクトリ（`<root>/<topic>-<日時>-<pid>/round-N/`）に、prompt.md・events.jsonl・stderr.txt・answer.md・result.json を保存する。各ラウンドの開始時と終了時の git の版（HEAD と、未追跡ファイルの中身を含む作業ツリーのハッシュ）も記録する
- 成功の判定: 終了コードが 0、最後のターンが `turn.completed`、回答が空でない、のすべてを満たすときだけ `status: ok`。タイムアウト（既定 1800 秒）は `timeout`、それ以外は `failed`
- 同じ相談の同時 resume をロックで防ぐ

### 手順

1. 依頼文を Write ツールで `<scratchpad>/codex/prompts/<topic>-<段階>.md` に書く（シェルの heredoc は使わない）
2. 中継サブエージェント `codex-relay` を Agent ツールで起動する。`description` は `Codex: <トピック> <段階>`（例: `Codex: ドーナツ順位 初回`、`Codex: PR#12 議論2`）にする。agent map にはこの名前が表示される。prompt にはコマンドだけを書く
   - 初回: `python3 -I ~/.claude/skills/codex-consult/run.py new --root <scratchpad>/codex --topic <ASCII のスラッグ> --model <model> --effort <effort> --cwd <対象リポジトリ。なければ scratchpad> --prompt-file <依頼文>`
   - 2回目以降: `python3 -I ~/.claude/skills/codex-consult/run.py resume --consult <初回の consult> --prompt-file <依頼文> [--model <model> --effort <effort>]`
3. 中継役は結果の JSON だけを返す。Codex の回答は、JSON の `answer_file` を Claude が直接読む（中継役の要約に頼らない）
4. `status` が `ok` でなければ「失敗時」に従う

中継役が使えない場合（サブエージェントとして動いていて Agent ツールがない場合など）は、`run.py` を Bash で直接実行する。その際は `run_in_background: true` で実行し、完了通知を待ってから結果を読む。

相談の経過を後から見るときは、consult ディレクトリの各ラウンドの prompt.md と answer.md（細かい経過は events.jsonl）を読む。`codex resume` を直接開くと安全のためのフラグが付かないので、使わない。

## モデルと effort

- 事実確認・軽い調査: `gpt-6.1-sol` / `low`
- 通常の判断・編集レビュー（標準）: `gpt-6.1-sol` / `medium`
- 難しい設計判断・根の深いバグ: `gpt-6.1-sol` / `high`
- 最重要の判断、または sol high で決着しない場合: `gpt-6-astra` / `medium`〜`high`
- `xhigh` / `max` / `ultra` と、上記以外のモデルは `run.py` が拒否する
- 議論の途中で根拠が足りない、または難しさが増したと分かった場合は、同じ相談のまま resume で `--model` / `--effort` を上げてよい。上げた理由を報告に書く。3往復の上限は、上げても数え直さない

## 初回はお互いの結論を見ずに出す

目的は、情報を広く集め、同じ情報源に偏った調査やレビューを避けること。そのため初回は Claude と Codex がそれぞれ独立に調べ、結論を出す。

1. Codex への初回の依頼を先に出してよい（並列に進めるため）。依頼文には Claude の結論も、Claude のメモの場所も含めない
2. その間に Claude も自分で調べる（手持ちの知識だけで済ませない）。複数の独立した情報源を当たり、結論・根拠・使った情報源を `<scratchpad>/codex/notes/<topic>.md` に書く
3. このメモを書き終えるまで、Codex の回答も途中のログも読まない。書き終えた後でメモを書き換えない
4. 両方がそろってから突き合わせる。Claude の結論を Codex に伝えるのは、2回目以降（resume）から

例外: コードレビューのように、Claude が何を意図して書いたかが判断に必要な場面では、意図（何を実現したいか）は伝える。結論（「この実装で問題ない」など）は伝えない。

## 依頼文の書き方

初回は次を含める。

1. 背景: タスクの目的、関連ファイルやコマンド
2. 判断してほしい点: 具体的な問いと評価の軸
3. 対象の版: レビュー対象が下書きなら、その全文を依頼文に含める。コードなら対象のコミットや差分の範囲を明記する
4. 制約: 「ファイルは編集しない。根拠はファイルの中身、コマンド出力、ドキュメントで示す。1つの情報源に頼らず、複数の独立した情報源を当たり、使った情報源を列挙する。事実と主観を分け、確認できない事実は未確認と書く。scratchpad 内の他の相談ログやメモは読まない。質問で返さず、不明点は仮定を明示して答える」

2回目以降は、これに加えて「Claude の説明は検証の対象であり、自分で確かめてから同意か反論をする」と書く。

## 版のずれを防ぐ

相談中も作業が進むので、Codex が見た版と実際に使う版がずれることがある。

- `result.json` の `changed_during` が true なら、相談中に対象が変わっている。変わった部分をもう一度確認させる
- `changed_during` が null（git 管理外、または版の取得に失敗）なら、版は確かめられていない。git 管理外の相談では依頼文に含めた内容が版になる。git 管理下で `snapshot_*` に `error` がある場合は、確認済みの版として扱わない
- 結果を採用する前に、`snapshot_after` と今のリポジトリの状態を比べる。相談後に対象が変わっていたら、変わった部分をもう一度確認させる
- PR / issue では、Codex が確認した下書きとユーザーに見せる下書きを同じものにする。確認後に書き直したら、差分をもう一度確認させる

## 結果の扱い

どの場合も、判断に影響する Codex の事実主張は Claude が自分で確かめる。

- **一致**: 双方の情報源を比べる。同じ情報源にしか頼っていなければ、別の情報源で確かめる。そのうえで進め、Codex の要点と情報源を短く報告する
- **補足・改善点**: 裏付けが取れたものを取り込み、何を取り込んだかを報告する。取り込まない点があれば、それは「意見が割れた」として扱う
- **意見が割れた**: 該当部分について Codex と議論する（下記）。割れていない部分は進めてよい

## 意見が割れたときの議論

同じ論点の議論は、初回の相談を resume して続ける。

- 双方とも、主張の前に事実確認を行う。ファイルの中身、コマンドの出力、ドキュメントなど、確認できる根拠で示す。推測で反論しない
- 相手の主張や根拠を、裏付けなしに信じない。Claude は Codex が示した事実を自分で確かめる（ファイルを読む、コマンドを実行するなど）。Codex にも、Claude の主張を自分で確かめるよう求める
- 議論の各往復で、新しい情報や別の視点を持ち込む。同じ情報を言い換えて反論し合わない。双方が同じ情報源に頼っていると気づいたら、そのことを指摘し、別の情報源を探す。Codex にも同じことを求める
- 新しく持ち込む情報も、共有する前に自分で事実確認する。確認できないものは事実として扱わず、未確認と明記する
- 自分で裏付けが取れた根拠に納得したら、立場を変えてよい。面子のために自分の案に固執しない
- どちらかが相手の意見に納得して合意できたら、ユーザーへの確認なしで合意した方針で進める
- 3往復で合意できなければ議論を打ち切り、ユーザーに判断を仰ぐ

### ユーザーへの報告

相談したら、議論の有無にかかわらず必ず報告する。

議論せずに済んだ場合（一致、または補足を取り込んだだけの場合）:

```
Codex の要点: <要点>
情報源: <双方が使った情報源>
取り込んだ点: <あれば>
```

議論して合意できた場合:

```
論点: <何について割れたか>
当初の意見: Claude <主張> / Codex <主張>
確認した事実: <議論中に確かめたこと>
情報源: <使った情報源。1つの情報源に偏っている場合はその旨>
合意: <どちらの案に、なぜ納得したか>
```

合意できなかった場合:

```
論点: <何について割れているか>

Claude の意見: <主張>
根拠: <根拠>

Codex の意見: <主張>
根拠: <根拠>

確認した事実: <議論中に確かめたこと>
情報源: <使った情報源。1つの情報源に偏っている場合はその旨>
残った対立点: <何が解消しなかったか>

トレードオフ:
- Claude 案: <利点と欠点>
- Codex 案: <利点と欠点>
```

- Claude は当事者なので、自分の側に寄せて書かない。両者の主張を同じ詳しさで書き、言葉の強さも揃える。Claude が折れた場合も、Codex が折れた場合も、同じように書く
- モデルや effort を上げた場合は、その理由も書く
- 合意できなかった場合の推奨は、ユーザーに求められたときだけ述べる。その際も当事者であることを明記する

## サブエージェントとして動いているとき

ユーザーには直接聞けない。そのため次のように動く。

- 議論は自分で行う。合意できたら進める
- 親には、作業結果とあわせて次の項目を必ず返す: 相談の状態（ok / 失敗 / 未完了）、当初の意見、確認した事実、合意内容または未解決の対立点、consult ディレクトリ
- 合意できなかった場合や相談に失敗した場合は、自分で決めずに上の項目を親に返す。親がユーザーへの報告と判断の依頼を行う

## 失敗時

`status` が `ok` でない場合は、`stderr_tail` などのエラー内容をユーザーに報告し、Codex なしで続けるか確認する（サブエージェントの場合は親に返す）。`timeout` の場合は、`--timeout` を延ばして新しく実行し直すことを提案してよい。同じ依頼を黙って何度も実行し直さない。
