# Codex 合議

Codex を read-only の相談役として呼び、独立した意見を得る。主導権は Claude Code が持つ。意見が割れたら事実確認をしながら議論し、合意できなければユーザーに判断を仰ぐ。議論の内容は必ずユーザーに伝える。

## 呼び出し方

プロンプトは常に stdin で渡し、最終回答は `-o` でファイルに受け取る。

```bash
codex exec --json -s read-only -m <model> -c model_reasoning_effort=<effort> \
  -C <作業ディレクトリ> -o <scratchpad>/codex-<topic>-1.md - \
  > <scratchpad>/codex-<topic>-1.jsonl <<'EOF'
<依頼文>
EOF
```

- `-s read-only` は必須。`workspace-write`、`danger-full-access` は使わない
- 原則として Bash の `run_in_background` で実行してターンを終え、完了通知を受けてから `-o` のファイルを読む。`low` の事実確認だけはフォアグラウンドでもよいが、その場合は `timeout: 600000` を指定する（既定の 120 秒では medium 以上の Codex が途中で止まる）
- 同じ論点を続けて議論する場合は、初回の jsonl の先頭行（`{"type":"thread.started","thread_id":"..."}`）の `thread_id` を使って再開する。`--last` は別のセッションを拾うおそれがあるので使わない。resume は `-s` を受け付けないので、sandbox は `-c` で指定する。モデルと effort は初回と同じにし、`-o` は毎回別のファイルにする

```bash
codex exec resume <thread_id> -c 'sandbox_mode="read-only"' -m <model> \
  -c model_reasoning_effort=<effort> -o <scratchpad>/codex-<topic>-2.md - <<'EOF'
<追加の依頼文>
EOF
```

- 別の論点では新しく実行する
- 編集レビューも同じ `codex exec` を使い、依頼文でレビュー対象（`git diff`、`git diff <base>...HEAD`、対象ファイルなど）を指定する。Codex は read-only でも `git diff` を実行できる。`codex exec review --uncommitted` はカスタムの依頼文と併用できないので使わない

## モデルと effort

- 事実確認・軽い調査: `gpt-6.1-sol` / `low`
- 通常の判断・編集レビュー（標準）: `gpt-6.1-sol` / `medium`
- 難しい設計判断・根の深いバグ: `gpt-6.1-sol` / `high`
- 最重要の判断、または sol high で決着しない場合: `gpt-6-astra` / `medium`〜`high`
- `xhigh` / `max` / `ultra` は使わない。上記以外のモデルも使わない

## 初回はお互いの結論を見ずに出す

目的は、情報を広く集め、同じ情報源に偏った調査やレビューを避けること。そのため初回は Claude と Codex がそれぞれ独立に調べ、結論を出す。

1. Codex を呼ぶ前に、Claude も自分で調べる（手持ちの知識だけで済ませない）。複数の独立した情報源を当たり、結論・根拠・使った情報源を `<scratchpad>/claude-<topic>.md` に書く。Codex の回答を読んだ後で書き換えない
2. Codex への初回の依頼文には、Claude の結論を含めない
3. 両方がそろってから突き合わせる。2回目以降（resume）で初めて Claude の結論を Codex に伝える

例外: コードレビューのように、Claude が何を意図して書いたかが判断に必要な場面では、意図（何を実現したいか）は伝える。結論（「この実装で問題ない」など）は伝えない。

## 依頼文の書き方

初回は次を含める。

1. 背景: タスクの目的、関連ファイルやコマンド
2. 判断してほしい点: 具体的な問いと評価の軸（例: 「この修正で再接続時の競合は解消するか」）
3. 制約: 「ファイルは編集しない。根拠はリポジトリの内容やコマンド出力で示す。1つの情報源に頼らず、複数の独立した情報源を当たり、使った情報源を列挙する。事実と主観を分け、確認できない事実は未確認と書く。質問で返さず、不明点は仮定を明示して答える」

## 結果の扱い

- **一致**: そのまま進め、Codex も同意したことを一言添える
- **補足・改善点**: Claude が自分で裏付けを取ったうえで取り込み、何を取り込んだかを報告する。取り込まない点があれば、それは「意見が割れた」として扱う
- **意見が割れた**: 該当部分について Codex と議論する（下記）。割れていない部分は進めてよい

## 意見が割れたときの議論

同じ論点の議論は、初回の `thread_id` で resume して続ける。

- 双方とも、主張の前に事実確認を行う。ファイルの中身、コマンドの出力、ドキュメントなど、確認できる根拠で示す。推測で反論しない
- 相手の主張や根拠を、裏付けなしに信じない。Claude は Codex が示した事実を自分で確かめる（ファイルを読む、コマンドを実行するなど）。Codex にも、Claude の主張を自分で確かめるよう求める
- 議論の各往復で、新しい情報や別の視点を持ち込む。同じ情報を言い換えて反論し合わない。双方が同じ情報源に頼っていると気づいたら、そのことを指摘し、別の情報源を探す。Codex にも同じことを求める
- 新しく持ち込む情報も、共有する前に自分で事実確認する。確認できないものは事実として扱わず、未確認と明記する
- 自分で裏付けが取れた根拠に納得したら、立場を変えてよい。面子のために自分の案に固執しない
- どちらかが相手の意見に納得して合意できたら、ユーザーへの確認なしで合意した方針で進める
- 3往復で合意できなければ議論を打ち切り、ユーザーに判断を仰ぐ

### ユーザーへの報告

議論をしたら、合意の有無にかかわらず必ず報告する。

合意できた場合:

```
論点: <何について割れたか>
当初の意見: Claude <主張> / Codex <主張>
確認した事実: <議論中に確かめたこと>
情報源: <使った情報源。1つの情報源に偏っている場合はその旨>
合意: <どちらの案に、なぜ納得したか>
```

合意できなかった場合:

```
論点: <何について割れているか>

Claude の意見: <主張>
根拠: <根拠>

Codex の意見: <主張>
根拠: <根拠>

確認した事実: <議論中に確かめたこと>
情報源: <使った情報源。1つの情報源に偏っている場合はその旨>
残った対立点: <何が解消しなかったか>

トレードオフ:
- Claude 案: <利点と欠点>
- Codex 案: <利点と欠点>
```

- Claude は当事者なので、自分の側に寄せて書かない。両者の主張を同じ詳しさで書き、言葉の強さも揃える。Claude が折れた場合も、Codex が折れた場合も、同じように書く
- 合意できなかった場合の推奨は、ユーザーに求められたときだけ述べる。その際も当事者であることを明記する

## サブエージェントとして動いているとき

ターンを終えると結果を受け取れず、ユーザーにも直接聞けない。そのため次のように動く。

- Codex はフォアグラウンドで `timeout: 600000` を指定して実行する
- 議論は自分で行う。合意できたら進め、報告を親に返す
- 合意できなければ自分で決めず、報告形式のまま親に返す

## 失敗時

codex が未インストール・未ログイン・エラー・タイムアウトの場合は、エラー内容をユーザーに報告し、Codex なしで続けるか確認する。
